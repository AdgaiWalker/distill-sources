事情经过

最早是在 0705 早上起来准备工作的时候，发现招商信用卡有一个 2000 多刀的账单的通知，感觉不对劲，但还不知道是如何产生的，但心里有点慌，于是立马打开 APP 去查看账单扣款来源：


发现是 Replicate 的扣款，然后去 Replicate 后台查看账单详情，发现 7 月份也已经被刷了 4000 多刀了


情急之下，没有继续往下排查，先做了快速止损：

1.
删除 Replicate 后台所有的 key，以防止继续被使用
2.
把billing 页面绑定的信用卡信息删除

因为 7 月付的账单需要到 8 月付才会扣，当时想的能减少一点损失是一点，但删除之后也不是很确定 8 月份的账单是否还会被正常扣除，但是我这边只能做到这里了，剩下的只能听天由命

把必要的止损做完之后，开始去排查账单都花在了哪里？


Replicate 显示 6 月产生了一张 $2,547.68 的账单，主要费用来自 black-forest-labs/flux-2-max 这个模型。具体拆开看：

•
input image megapixels：$975.72
•
output image megapixels：$906.96
•
runs：$664.68

更吓人的是，7 月账单页面还挂着一笔 $4,283.29 ，状态是「进行中」。两笔加起来 将近 $6,800 ，都来自同一个模型的消耗


但我自己平时用 Replicate 的量非常低。后来 Replicate 支持也确认了， 这段时间我自己的真实用量不到 1 美元 。

他们调查后给的结论是：一个「不属于我正常设置」的 token 在 6 月 17 日出现，然后高频跑 black-forest-labs/flux-2-max ，一直刷到 7 月 1 日才停。

所以这不是什么业务增长、也不是我自己不小心多调了几次——就是 API token 被第三方盗用了 。


查到原因之后，也不知道怎么办，于是去微信群中查了看是否也有其他人遇到了这种情况，确实有，但金额都没有我这么大，而且能否追回也没有定论，当时觉得要不就这样吧，吃一堑长一智，当涨经验了，这事儿就暂时搁置了。

但由于金额比较大，又不太甘心，当天晚上也没有睡好，想试着给官方发邮件，但又不确定会不会收到回复，然后跟 GPT 聊了一下我的情况，问了一些担心的问题，也让 AI 搜了下有没有相关的案例：




结果 GPT 真给找到了一个案例： 有人因为 Vite 前端泄露 Gemini key，被刷约 $2,200，同步发 support ticket 和论坛帖 ，虽然不是 Replicate，但情况类似，于是又让 GPT去查看这个案例，学习了一下要求退款的文案还有理由


有了这个之后，决定按照这个案例的方式去给官方发邮件试试看，到 0706 晚上，把所有需要的资料和截图等都整理好之后，让 GPT 给写了一封详细的邮件，详细说明了我遇到的问题，并在结尾提出了我的诉求，把发票也作为附件一并发送过去了


发完之后就是漫长的等待时间，一度以为石沉大海了，没想到在 0718 收到了官方的回复，说他们会去调研


一看感觉有希望，但为了尽可能的争取到退款，收到这个邮件之后，我又回复了一封邮件，重新提了一下我的诉求


接下来又是漫长的等待，终于在 0808 收到了明确的调查结论，确认是盗刷，然后说会退回 6 月份的扣款和作废 7 月份的账单


至此，整个从发现到最终全部退款的流程就结束了，历时一个多月

最终复盘

第一，API Key 本质上就是钱，保护好自己的 API key

只要某个平台按调用量计费，API Key 泄露就等于银行卡暴露在外。尤其是图像、视频、GPU 推理类 API，单次调用价格可能不高，但脚本可以在短时间内刷出非常大的账单。

第二，平台不一定会自动帮你兜底。

这次 Replicate 后来处理得还算负责，最终退款并 void 了后续账单。但他们也明确说：这次异常不是他们主动发现的，而是我上报后才处理。也就是说，不能假设平台一定会及时发现异常用量。

第三，账单提醒和硬性限额很重要。

如果平台没有消费上限，就要自己做保护：

•
绑定虚拟卡或低额度卡。
•
开启银行侧消费提醒。
•
使用可以设置单商户限额的卡。
•
平台侧开启 usage/billing alert。
•
定期检查 token 和账单。
•
对高风险 API 做自己的限流和额度控制。

我以后会怎么做

这次之后，我会对所有按量计费服务做一轮清理：

•
删除不用的 API token。
•
每个项目单独创建 token，不共用主 token。
•
token 权限最小化。
•
定期 rotate secret。
•
所有 key 只放服务端，不进前端。
•
给 AI/GPU 类服务绑定低额度虚拟卡。
•
开启账单提醒。
•
对关键 API 调用加每日额度。
•
把异常账单检查加入日常运维清单。

结论

这次事故最终没有造成实际经济损失，但教训很直接：

API Key 不是普通配置项，而是支付凭证。

尤其是 AI、GPU、云服务这类按量计费平台，一旦 key 泄露，几小时或几天内就可能产生几千美元账单。平台可能会帮你处理，但更可靠的方式还是从架构上降低风险：不要把 key 放前端，不要使用无限额度付款方式，不要等到账单来了才发现问题。

还有就是如果真遇到了，还是要准备好证据链去积极申诉，不要觉得可能追不回来就认栽了，这次如果没有积极的去申诉沟通的话，肯定这笔损失就只能自己承担了
