做独立站的都要发外链。目录站几百个,一个个手填表单太耗人,自然会想到写个 agent 自动投。

我给自己的站写了这么一套东西:探测目录站有没有提交入口 → 核验入口是真的 → LLM 驱动浏览器填表提交。跑了2天,投出去 66 个站。

然后我翻日志,看到大量这样的记录:


代码块
JavaScript
goodfirms.co 没投出去 agent_submit(LLM-in-loop 2步) | Cloudflare 安全验证无法通过

两步就收工。 一共 239 条失败记录,粗看有 37 条跟 Cloudflare 有关。

下面是把它拆开的全过程。

我抽了几个"Cloudflare 失败"的站实测,curl 抓下来一看, econerre.it 、 huntinglocator.com 、 smartmanagement.bg 全是 Attention Required —— 硬拦。huntinglocator.com

拿去喂打码平台,直接被打回:


代码块

ERROR_INVALID_TASK_DATA: Cloudflare challenge not found!

这类站不用再花力气了。 我还换了完全不同的出口 IP(机场节点 vs 家庭宽带)各试一遍,拿到的是 一模一样的 403 。这直接排除了 IP 的问题 —— 是站方的规则拒绝了我们这类请求本身,换多少个 IP 都一样。

实操建议:遇到 Cloudflare 先 curl 一下看响应体。 Attention Required 就归档别碰, Just a moment 才值得往下做。这一步能帮你省掉大半的无用功。

这不是被 Cloudflare 打败,是我们自己没能力应战就认输了。

更打脸的是: goodfirms.co 我用最普通的 urllib 请求,返回 200 。页面根本能打开。是我们的自动化浏览器触发了挑战,而普通 HTTP 请求不会。

再往下查,37 个"Cloudflare 失败"的站里, 21 个用普通 HTTP 就能正常打开 。它们从来不是"打不开页面",是 agent 填表提交时才出的问题,却全被笼统记成了"Cloudflare 安全验证无法通过"。

这里有个通用教训: 失败归类要基于证据链,不能基于最后一条报错 。最后一条报错往往是表象,中间步骤才是真相。我这套系统 42% 的失败连原因都没记,这才是最大的问题。


三、cf_clearance 绑 IP —— 这是全场最贵的一课

剩下的挑战页站怎么办?思路是用打码平台的 AntiCloudflareTask :它替你做完那道题,返回一个 cf_clearance cookie,你把 cookie 塞进浏览器就能过。

我把这条路打通了,然后收到这个报错:


代码块
JavaScript
Solve failed. Please check if the userAgent and proxy IP you sent match those in your code.

cf_clearance 是和「解题时用的 IP + UA」绑定的。

而我的情况是:



走哪条路



出口 IP




我的浏览器(走机场代理)



188.xxx.xxx.xx




打码平台(走我家宽带)



1xx.64.2xx.xxx

打码平台用我家宽带 IP 解出来的票,拿给一个跑在机场 IP 上的浏览器用 —— Cloudflare 当然不认。

更麻烦的是我的代理还带节点轮换,浏览器 IP 一直在变, 永远不可能对上 。

解法:两个 SOCKS5,同一个出口

这里有个具体的技术约束: Chromium 不支持带认证的 SOCKS5 代理 (直接报 Browser does not support socks5 proxy authentication )。而暴露在公网的代理又必须有认证,否则谁都能白嫖。

所以要开两个口,共用同一个出口:


代码块
JavaScript

•
公网口 :用户名 + 32 位随机密码,端口白名单只放 80/443,禁止连内网地址,连续失败封 IP。给打码平台从外网拨进来。
•
内网口 :免认证,但 只接受本机 IP 的连接,外网完全不可达。给 Chromium 用。

两个口跑在同一台机器上(我放在 NAS 上),出口自然一致。实测:


代码块
JavaScript
浏览器经内网口 → 1xx.64.2xx.xxx
打码平台经公网口 → 1xx.64.2xx.xxx ✅ 一致

改完之后,同一个站的对比:


代码块
JavaScript
改之前: S1 撞 CF → 无公网代理 → S2 认输
改之后: S1 点首页 → S2 点 Get Listed → S3 注册表单已填提交 → S4 撞验证码

Cloudflare 这一关过了。 卡点变成了注册页的验证码,那是另一个问题。


四、顺手挖出来的两个坑

调试过程中撞见两个 bug,都挺典型:

坑一:一个类型判断没做,打穿整条流程

处理下拉框选择时,代码直接 [...select.options] 。但很多站用 div / ul 自己搭下拉,那玩意儿没有 .options ,展开就抛:


代码块
JavaScript
TypeError: s.options is not iterable

这个异常从浏览器求值层冒出来会 打穿整个投放循环 ,整站直接判失败 —— 而实际上表单已经填到第 7 步了。

修法不只是加个判断,还要给自造下拉一条退化路径:点开它,再在浮层里点包含目标文字的那一项。

坑二:抓 sitekey 抓到了空壳

解 reCAPTCHA 要先拿到页面的 sitekey 。原代码是找第一个 URL 含 recaptcha 的 iframe。

但 reCAPTCHA 在页面上会插 两个 iframe:真正的挑战框是 api2/anchor?k=<sitekey> ,还有一个叫 api2/aframe 的空壳 —— 它没有 k 参数 ,而且按 DOM 顺序常排在前面。

于是抓到空壳,拿到一段不是 key 的东西,打码平台打回:


代码块
JavaScript
invalid websiteKey, its length should be 40

修法有个很好用的硬约束: reCAPTCHA 的 sitekey 恒为 40 字符 ( 6L 开头 + 38 位)。把所有候选来源( data-sitekey 属性、非 aframe 的 iframe、 ___grecaptcha_cfg 运行时配置、页面 HTML 正则)全收集起来,只留长度正好 40 的,基本不会错。


五、这一晚上真正的收获

要说技术成果,其实就一句话: 两个 SOCKS5 共用同一出口,让打码平台和你的浏览器在 Cloudflare 眼里是同一个人。 其实我需要用两个 socks5 也是因为我把它部署在了我的 nas 上，但是我的 nas 默认是走tailscale的，所以也和家宽出口不一致。

总结几条经验:

1.
先分清"有题可做"和"直接被拒" ,后者省下来的时间比什么优化都多。
2.
失败归类要看证据链,不要看最后一条报错。 我 37 个"Cloudflare 失败"里只有 8 个真是 Cloudflare 的事,而这 8 个还是我们自己没能力应战。
3.
绑 IP 的凭证,拿的时候和用的时候必须同一个出口。 这个坑不只在 Cloudflare,任何"解题拿票"的场景都一样。
4.
别急着上更贵的方案。 我一开始想的是"Cloudflare 太强要加钱",实际是配置里少了一个字段。

最后说个数字,免得看着像成功学:这套系统跑到现在 2 天了,66 次真实提交换来 2 条 实测活着的 dofollow 外链。这里面还是有太多细节需要调整，得慢慢摸索着来。
