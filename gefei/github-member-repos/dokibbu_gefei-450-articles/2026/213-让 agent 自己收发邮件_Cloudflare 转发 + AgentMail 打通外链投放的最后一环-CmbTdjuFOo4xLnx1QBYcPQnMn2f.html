做外链投放自动化,你很快会撞上一堵墙: 目录站要你注册账号,注册要验证邮箱。

agent 填完表点提交,站方回一句"验证链接已发到你邮箱"。然后呢?没有然后了 —— 脚本看不到邮箱,流程断在这。

我最后是用 Cloudflare Email Routing + AgentMail 把这一环补上的,现在 agent 能自己注册、自己收验证信、自己点链接激活、自己认领站方后续的通知。这篇讲怎么搭,以及中间踩的几个坑。


一、为什么不能随便找个邮箱了事

最直觉的做法是给 agent 一个 Gmail 或 QQ 邮箱,用 IMAP 读。我一开始就是这么干的,跑起来之后发现三个问题:

问题一:分不清哪封信是哪个产品的。

如果你手上不止一个站,所有目录站的回信都堆进同一个邮箱。发件人是 noreply@somedirectory.com ,主题是 "Your submission has been received" —— 这封信到底是哪个产品的提交回执?靠猜。noreply@somedirectory.com

问题二:邮箱地址泄露给几十个目录站。

你的主邮箱会被写进几十个目录的数据库。这些站本身就是做 SEO 的,名单转手是常事。

问题三:业务号被风控。

我在另一个项目上吃过亏 —— 用常用账号跑自动化,直接被锁号。


二、架构:一个域名邮箱 + 一个 agent 信箱

最终的形态很简单:


代码块
JavaScript
目录站发信 → contact@产品域名 (产品专属地址,写在提交资料里)
↓
Cloudflare Email Routing (免费转发,原始 To 头保留)
↓
agent 信箱 (AgentMail) (有 API,脚本直接读)
↓
mail_sweeper 常驻进程 (LLM 判意图 → 安全闸 → 写回状态)

关键在于 每个产品一个专属地址 :

•
产品 A → contact@产品A域名
•
产品 B → contact@产品B域名

这些地址全部转发到同一个 agent 信箱。脚本读信的时候,看 To 头 就知道这封信属于哪个产品 —— 不用猜、不用按发件域反查投放记录。

Cloudflare 这边怎么配

Email Routing 在 Cloudflare 面板里是免费的,前提是域名托管在 CF:

1.
域名 → Email → Email Routing → 启用
2.
它会自动加三条 MX 记录( route1/2/3.mx.cloudflare.net )
3.
加一条转发规则: contact@你的域名 → 你的 agent 信箱
4.
目标地址要点邮件里的链接确认一次

配完 dig +short MX 你的域名 应该能看到那三条 CF 的 MX。

免费额度对这个场景绰绰有余 —— 目录站的回信一天也就几封。

agent 信箱选 AgentMail 的原因

它是给 agent 用的邮箱服务,有 REST API,读信一行代码:


代码块
Python
from agentmail import AgentMail
client = AgentMail(api_key=KEY)
msgs = client.inboxes.messages.list(inbox, limit=25)

不用折腾 IMAP、不用处理 OAuth 过期、不用担心"这个登录看起来不安全"。

我实际上是 双信箱并行 的:AgentMail 一个,另一个走 QQ 邮箱的 CLI 工具。两个信箱的消息合到一起处理,加了各自的前缀( am: / qq: )做 message_id 去重。多一条通道多一层保险 —— 某一家抽风的时候另一家还在。


三、收到信之后:让 LLM 判意图,规则只做安全

目录站的回信五花八门:验证链接、收录通过、拒绝通知、要你挂徽章、要你补资料、退信、还有一堆营销周刊。

我试过用关键词规则分类,很快就放弃了 —— 各家措辞差太远。现在是 LLM 判意图,规则只做安全闸 :


代码块
JSON
{"kind": "verification_link|approved|rejected|badge_request|info_change|bounce|noise",
"site_domain": "这封信对应的目录站域名",
"action": "open_link|record_only|ignore",
"verify_url": "正文里的验证链接原文",
"summary": "一句话结论"}

判出来之后按 kind 分流:验证链接就去点、通过就把投放状态改 success 等终核、拒绝就改 failed、要徽章就标记出来等人工决定。

这里有个必须讲的安全问题

邮件正文是攻击者可控的。 任何人都能给你的 contact@ 地址发信,信里放一个链接说"请点击验证"。如果 agent 见链接就点,那就是个开放的 SSRF。

所以点链接之前有四道闸, 全过才点 :

1.
只处理库里打过交道的站 —— 发件站必须在我们的投放记录或账号表里。素不相识的站发来的信一律不点。
2.
链接的注册域必须等于发件站,且路径含验证关键词 ( verify / confirm / activate / 激活 …)。
3.
链接必须字面出现在原始正文里。 这条是防 LLM 的 —— verify_url 是 LLM 从攻击者可控的正文里"推导"出来的,不能直接采信。LLM 合成出来的地址一律不认。
4.
逐跳校验重定向。 只查最终 URL 是不够的 —— 站方/verify → 攻击者/collect?token=x → 站方/done 这种链路,最终 URL 看着人畜无害,但 中间那一跳已经把请求发出去了 ,token 已经泄了。所以每一跳都要单独校验 host,出域立即中止。

另外:只发 GET、限 200KB、限 5 跳、TLS 证书必须有效。

同域判断别自己写

我在这里栽过一次。原来判"链接是不是同域"用的是"取域名最后两段比较",于是:


代码块
JavaScript
evil.co.uk vs somedirectory.co.uk → 两段都是 "co.uk" → 判定同域 ✅通过

任意 .co.uk 域名都能通过同域校验。 后来还发现库里躺着 co.uk 这种伪站点记录。co.uk co.uk

正确做法是用 公共后缀列表(Public Suffix List) ,这是 Mozilla 维护的权威清单,明确列出哪些后缀是"公共"的( co.uk 、 com.cn 、 github.io 都在里面)。别手写启发式规则,这类判断的边界情况多到超乎想象。co.uk com.cn


四、幂等:这一步不做,后果比你想的严重

每封信处理完要记下 message_id,下次跳过。听起来是小事,但漏掉会很难看:

•
验证链接被重复点击(有的站会因此失效)
•
投放状态被反复改写
•
站方看到你反复触发同一个动作

我这边的实现是把已处理的 message_id 存成 JSON 文件。这里有两个细节:

别做有损截断。 我原来写的是 sorted(已处理)[-3000:] —— 想着控制文件大小。但 message_id 不是按时间排序的,按字典序排完截尾, 会丢掉任意一批已处理记录 ,那些信下轮就被重新处理了。

要原子写。 直接 open(path, "w") 写到一半崩溃,得到的是个空文件,等于全量重跑。正确做法是写临时文件 + os.replace() (同盘 rename 是原子的)。


五、注册这一环:每个站独立账号

有了能收信的邮箱,注册就通了。agent 遇到"必须登录才能提交"的站,流程是:

1.
用产品专属邮箱注册
2.
站方发验证信 → 转发到 agent 信箱 → mail_sweeper 认出来 → 点链接激活
3.
账号信息存进凭据文件(域名 → 用户名/邮箱/密码/注册日期)
4.
下次投同一个站直接登录

凭据文件我这边已经攒了 34 个站点账号 。

两个容易忽略的点

凭据文件要加锁。 我这个文件里躺着 34 个站点账号 + 几个 API 密钥。有一次差点出事:读取函数写的是 try: json.load(...) except: return {} —— 看着无害,但如果文件读到一半失败(JSON 少个逗号、或者撞上别的进程正在写),它就静默返回空字典, 紧接着一存,34 段全没了 。而注册账号是补不回来的。

改成:只有"文件不存在"才算空,其余读失败一律抛出来。另外读-改-写整段要加文件锁,不然两个进程并发写会丢段( os.replace 保证文件不会写一半,但拦不住"我读到 34 段 → 别人写进第 35 段 → 我把 34 段写回去")。

账号创建这件事本身要人来拍板。 这是我后来加的纪律 —— 代表你在第三方站建账号,不该由脚本自己决定。现在的做法是识别到需要注册就停下来,等人确认。

这套东西解决的是**"流程断在邮箱"**这个具体问题。它不会让你的外链数字暴涨 —— 目录站外链的转化率本来就低。但在它之前,凡是需要注册的站(我这边有 46 个)一个都投不进去;有了它,这条路至少是通的。

一个还没解决的坑

我建这套东西之前,已经有 34 个账号是用旧的通用邮箱注册的。新的"每产品一个地址"约定只对 之后 的注册生效。已经注册的那批要迁移,得逐个站改邮箱 —— 这活还没干。

如果你要搭,一开始就按产品分地址。 后补迁移比一开始就分要麻烦得多。


附:配置清单

想照着搭的话,需要这些:

1.
域名托管在 Cloudflare(Email Routing 的前提)
2.
一个 agent 邮箱服务(AgentMail 或同类,要有 API)
3.
一个能调 LLM 的通道(判邮件意图用,每封信一次调用,很便宜)
4.
Public Suffix List 的数据(判同域用,Mozilla 官方维护,可以生成成代码里的静态表)

整套跑在一个常驻脚本里,15 分钟一轮。
